# Mini Mechanic Service App

An Android app for **Instant Mechanic**: browse nearby garages, open one for full
details, and request a vehicle service. Built with Kotlin and Jetpack Compose on an
MVVM + clean-architecture foundation, backed by a real REST API with offline caching.

Submission for the Android Development Internship assignment.

## What it does

**Home** — a list of garages showing name, rating, distance, locality, the services
each offers, and a live Open/Closed badge. Search by garage name, area or service;
filter to open-now; sort by nearest, top rated or name. Loading, error-with-retry and
empty states are all handled.

**Mechanic details** — garage name, rating and review count, full address with
distance, every service offered, a seven-day working-hours table with today
highlighted, and a tappable phone number that opens the dialer.

**Request service** — a form for customer name, phone, vehicle number, service (a
dropdown pre-filled from that garage's own offerings) and problem description. Every
field is validated with inline errors. On submit the request is `POST`ed to the API
and a confirmation appears with the real request reference returned by the server.

### Notes on the data

**`createdAt` and `avatar` are injected by mockapi** and were never sent by the app.
The JSON parser is therefore configured with `ignoreUnknownKeys = true`; without it,
deserialization fails on fields the app does not model. There is a unit test that
feeds a payload containing both keys to prove this holds.

**The 10 garages were seeded deliberately via `POST`,** not generated by mockapi's
faker. Auto-generated records proved unstable — the same `id` returned a different
person's name on consecutive requests — whereas records created through `POST`
persist correctly. The seeded data covers a deliberate spread: ratings from 3.6 to
4.8, two to five services each, and three working-hours patterns (weekdays-only,
seven-day long hours, and closed Mondays) so the Open/Closed logic and the filters
have something real to act on.

**Every DTO field except `id` is nullable with a default.** A record missing a field
would otherwise throw `MissingFieldException` and empty the entire list; instead the
mapper drops just that record.

### Using your own endpoint

Create a mockapi.io project with resources named `mechanics` and `serviceRequests`,
then change `BASE_URL` in `app/build.gradle.kts`. The schema does not need
configuring — mockapi accepts arbitrary fields on `POST`, so seeding the mechanics
resource with records shaped like the one above is enough.

## Architecture

Clean architecture in a single Gradle module, layered by package. Dependencies point
inward — `presentation → domain ← data` — so the domain layer knows nothing about
Retrofit, Room or Compose and cannot break when the API or database changes.

```
com.minimechanicserviceapp
├── core/result/          AppResult, DataError, exception → error mapping
├── domain/               ← depends on nothing
│   ├── model/            Mechanic, WorkingHours, OpenStatus, ServiceRequest
│   ├── repository/       repository interfaces
│   ├── usecase/          GetMechanics, GetMechanicById, Refresh, SubmitRequest
│   ├── utill/            OpenStatusResolver, DistanceCalculator, UserLocation
│   └── validation/       ServiceRequestValidator
├── data/                 → implements domain interfaces
│   ├── remote/           Retrofit API + DTOs
│   ├── local/            Room database, DAO, entity, type converters
│   ├── mapper/           DTO → Entity → domain model
│   └── repository/       repository implementations
├── di/                   Hilt modules: Network, Database, Repository
└── presentation/         → depends on domain only
    ├── home/             HomeScreen, HomeViewModel, HomeUiState
    ├── details/          MechanicDetailsScreen, DetailsViewModel
    ├── request/          RequestServiceScreen, RequestViewModel
    └── navigation/       type-safe destinations + NavHost
```

47 source files and 13 test files.

### MVVM and state

Each screen has one ViewModel exposing a single `StateFlow<UiState>`. The UI is
stateless: a `…Route` composable owns the ViewModel and passes plain data plus
callbacks to a `…Screen` composable, which can be previewed and tested without Hilt.

The visible mechanic list is **computed** inside a `combine` of the cached data, the
search/filter/sort controls and the load state. It is never stored as a second list,
so it cannot drift out of sync with the source of truth.

### Offline-first data flow

```
Compose  ←  StateFlow  ←  ViewModel  ←  UseCase  ←  Repository  ←┬─ Room  (source of truth)
                                                                 └─ Retrofit (writes through)
```

Reads always come from Room as a `Flow`, so the UI renders cached garages instantly on
a cold start and updates itself when new data lands. `refreshMechanics()` fetches from
the network and writes through to Room; the UI reacts to the database, never to the
network response directly. The cache write is a single `@Transaction` that clears then
re-inserts, so a mid-write failure cannot leave a half-populated list, and a garage
removed server-side actually disappears locally.



**The repository is tested over real HTTP.** `MechanicRepositoryImplTest` runs against
MockWebServer and asserts each failure maps to the right typed error: a 500 and a 404
to `Server(code)`, malformed JSON to `Serialization`, an unreachable server to
`NoInternet`. It also verifies that a failed refresh leaves previously cached rows
intact, and that one malformed record is skipped while its siblings survive.

**Time is injected, not read.** `OpenStatusResolver.resolve(hours, now)` takes `now` as
a parameter, which is what makes "closed at 07:00, opens at 09:00" assertable instead
of dependent on when the suite happens to run.

**Route arguments are read by property reference,** not `toRoute<T>()`. `toRoute`
constructs an `android.os.Bundle` internally, which throws
`Method putCharSequence in android.os.Bundle not mocked` and takes down every test in
the class at construction. Using `savedStateHandle[Destination::mechanicId.name]`
keeps the lookup compile-checked while remaining testable on a plain JVM — which is
why `RequestViewModelTest` runs 14 tests with no Robolectric.

Fakes stand in for both repositories and the DAO. `FakeMechanicDao` deliberately does
**not** override `replaceAll`, so the interface's own clear-then-insert body is the
code under test, exactly as in production.

## Assumptions

**Distance is computed, not supplied.** The assignment asks to display distance but
location permissions were out of scope, so the app does not read GPS. Each garage
carries `latitude`/`longitude`, and distance is calculated with the haversine formula
against a fixed reference point — central Bengaluru, in `domain/utill/UserLocation.kt`.
Swapping in a real `FusedLocationProviderClient` would mean changing that one object;
nothing else in the app would need to know. This felt more honest than storing a
hardcoded `"2.4 km"` string in the JSON.

**Open/Closed is derived, not stored.** Rather than trusting an `isOpen` boolean in the
API, status is computed by comparing the current time against the garage's working
hours. When closed, the app also reports when it next opens, rolling forward across
days. This is why the seeded data includes garages closed on Mondays — so the logic is
visibly doing something.

**Vehicle numbers follow the Indian plate format** (`KA01AB1234`), validated against
`^[A-Z]{2}[0-9]{1,2}[A-Z]{1,3}[0-9]{1,4}$`. Input is normalised before validation, so
`ka-01 ab 1234` is accepted and stored canonically.

**Phone numbers are treated as 10-digit Indian mobile numbers** starting 6–9. A `+91`
or leading `0` prefix is stripped during normalisation, so `+91 98765 43210` and
`09876543210` are both accepted.

**Tapping the phone number opens the dialer, it does not place the call.**
`ACTION_DIAL` requires no `CALL_PHONE` permission, which keeps the app's permission
list to just `INTERNET` and `ACCESS_NETWORK_STATE`.

**The confirmation is a state of the request screen, not a separate route.** The real
record id returned by mockapi is shown as the reference number, which is what
demonstrates the `POST` actually reached the server.

**The `avatar` URL that mockapi attaches to each record is deliberately unused.** They
are randomly generated person portraits, not photographs of garages, so putting them
on the cards would look like a bug rather than a feature.



## Known limitations

Listed plainly rather than left for a reviewer to discover.

**Not yet run on a physical device.** `assembleDebug` is clean and the 74 unit tests
pass, but the Compose layouts are compile-verified only — the wireless debugging
connection to the test device dropped during development and could not be recovered
from the shell. Screenshots and the demo recording are outstanding for the same
reason. Nothing here is known to be broken on-device; it simply has not been confirmed.

**Pull-to-refresh is plumbed but not surfaced.** `HomeViewModel.refresh()` accepts an
`isPullToRefresh` flag and `HomeUiState.isRefreshing` is maintained correctly, but no
`PullToRefreshBox` consumes it yet, so the only way to retry from the UI is the button
on the error state. The state layer is ready; the gesture is not wired.

**No instrumented or UI tests.** The `androidTest` source set is empty. Testing effort
went into the logic that can fail silently — mappers, open/closed derivation, error
mapping, ViewModel state — rather than into Compose UI assertions.

**UI strings are inline literals**, not string resources, so the app is not
localisable. `strings.xml` holds only the app name.

**Room uses `fallbackToDestructiveMigration`.** The schema is version 1 with no
migrations, so a future schema change would drop the cache and refetch. Acceptable for
a cache whose source of truth is remote; not acceptable for user-authored data.

**Distance is measured from a fixed point,** so every user sees identical distances.
See *Assumptions* above.
